PRACTICA 9: Conexiones y pruebas de base de datos entre dispositivos con la misma aplicación

Una empresa de desarrollo de software está construyendo una aplicación móvil para administrar incidencias técnicas. Los empleados utilizan la misma aplicación desde diferentes dispositivos para registrar, consultar y actualizar incidencias en tiempo real.
Actualmente, cada dispositivo puede mostrar información distinta. Por ejemplo, un empleado registra una incidencia desde su teléfono, pero otro empleado no puede verla desde su dispositivo. En otros casos, dos usuarios modifican simultáneamente un mismo registro y la información final no corresponde a lo esperado.
La empresa necesita comprobar que la aplicación se conecte correctamente a una base de datos compartida, que los cambios realizados desde un dispositivo puedan consultarse desde otro y que las operaciones de escritura, actualización y eliminación se comporten de manera consistente.
El equipo de estudiantes asumirá el papel de ingenieros de software responsables de validar la conectividad, persistencia y sincronización de datos entre dispositivos móviles.
La práctica se realizará utilizando la misma aplicación instalada o ejecutada en dos dispositivos Android. Ambos deberán acceder al mismo proyecto de base de datos, no a dos bases independientes.

OBJETIVO
Implementar y validar la conexión de dos dispositivos móviles a una base de datos compartida mediante una misma aplicación, ejecutando pruebas funcionales y de consistencia para verificar la creación, consulta, actualización, eliminación y sincronización de datos, así como el manejo de conflictos y de interrupciones de conectividad.

Configurar una aplicación móvil para conectarse a una base de datos remota.
Diferenciar entre almacenamiento local y almacenamiento compartido en la nube.
Verificar que varios dispositivos consulten la misma colección de datos.
Comprobar la propagación de cambios entre dispositivos.
Identificar problemas de sincronización y actualización de información.
Evaluar el comportamiento de la aplicación cuando dos dispositivos modifican un mismo registro.
Probar la persistencia de datos después de cerrar y abrir la aplicación.
Documentar resultados, defectos y evidencias de las pruebas.
Fase 1. Verificación de conectividad
1. Ejecuta la aplicación en el dispositivo A.
2. Ejecuta la misma aplicación en el dispositivo B.
3. Comprueba que ambos puedan acceder a la pantalla de incidencias.
4. Verifica que los dos dispositivos estén conectados al mismo proyecto de Firebase.
5. Consulta la colección incidencias desde Firebase Console.
6. Registra el estado inicial de la colección.

Fase 2. Prueba de escritura y lectura cruzada 
1. Desde el dispositivo A, registra una incidencia con título PRUEBA_A_001.
2. Confirma que la aplicación muestre el resultado de la operación de guardado.
3. Verifica que el documento exista en Firestore.
4. Desde el dispositivo B, consulta la lista de incidencias.
5. Localiza PRUEBA_A_001.
6. Registra si apareció automáticamente o si fue necesario actualizar la consulta.
7. Repite el procedimiento creando PRUEBA_B_001 desde el dispositivo B.
8. Comprueba que el dispositivo A pueda recuperar el segundo registro.

Fase 3. Actualización y sincronización
1. En el dispositivo A, cambia el estado de PRUEBA_A_001 de Pendiente a En proceso.
2. Confirma que el cambio se haya guardado.
3. Observa el dispositivo B.
4. Comprueba si muestra el nuevo estado y cuánto tarda en reflejarlo.
5. Si la aplicación no actualiza automáticamente, ejecuta el mecanismo de consulta definido.
6. Desde el dispositivo B, cambia la prioridad a Crítica, si esa prioridad está contemplada en las reglas del ejercicio.
7. Vuelve a consultar el registro desde el dispositivo A.
8. Verifica los valores finales en Firestore.

Fase 4. Prueba de conflictos
Esta fase evalúa un escenario más avanzado: dos dispositivos modifican el mismo documento.
1. Selecciona una incidencia de prueba.
2. Abre el mismo registro en ambos dispositivos.
3. En el dispositivo A, modifica el estado a En proceso, pero no guardes todavía si la aplicación permite separar edición y guardado.
4. En el dispositivo B, cambia la prioridad a Alta y guarda.
5. En el dispositivo A, guarda la modificación pendiente.
6. Consulta el documento final desde ambos dispositivos y desde Firestore.
7. Registra qué campos se conservaron y cuáles cambiaron.

Fase 6. Cierre y análisis
1. Completa la matriz de pruebas.
2. Compara los resultados observados con los esperados.
3. Identifica al menos un riesgo de sincronización o explica por qué no se detectaron defectos en las condiciones evaluadas.
4. Recopila las evidencias.
5. Redacta una conclusión técnica breve.

PRACTICA 11: Pruebas de Whitebox

Cada estudiante realizará una auditoría técnica de su propia aplicación móvil desarrollada en Flutter o Kotlin, aplicando técnicas de pruebas White Box para evaluar el funcionamiento interno del software y no solamente su comportamiento visual.

La evaluación abarcará tres componentes de la solución:
1. Sitio web o servicio web: frontend web, backend, API REST o servicios que formen parte del proyecto.
2. Aplicación móvil: lógica de negocio, navegación, validaciones, consumo de servicios, manejo de errores y rendimiento.
3. Base de datos: operaciones CRUD, consultas, integridad, consistencia, seguridad y rendimiento.
Además, se evaluará la comunicación entre los componentes, incluyendo latencia, ping, tiempo de respuesta, tasa de transferencia, códigos HTTP, tamaño de las respuestas y comportamiento ante pérdidas de conectividad.

Demostrar mediante evidencias técnicas que la aplicación funciona correctamente desde su estructura interna, que sus componentes se comunican de forma eficiente y que los datos mantienen su integridad durante todo el proceso.

NO SERÁ SUFICIENTE mostrar capturas de pantalla de la aplicación funcionando. El estudiante deberá presentar evidencias obtenidas del código fuente, herramientas de depuración, registros de ejecución, pruebas automatizadas y mediciones de rendimiento.

Objetivos específicos
- Analizar las estructuras de control, condiciones, métodos y rutas de ejecución del código.
- Medir la cobertura de instrucciones, decisiones y condiciones.
- Identificar errores de lógica, excepciones no controladas y defectos de validación.
- Evaluar las comunicaciones entre aplicación, servidor y base de datos.
- Medir latencia, ping, tasa de transferencia y tiempos de respuesta.
- Validar códigos HTTP, estructura de respuestas y consistencia de datos.
- Detectar consultas ineficientes, problemas de concurrencia y vulnerabilidades.
- Elaborar un informe de calidad con evidencias y propuestas de corrección.

Herramientas complementarias:
- Git para identificar la versión del código evaluado.
- Postman o Insomnia para probar endpoints.
- Wireshark, cuando se tenga autorización y acceso a la red de pruebas.
- JMeter, k6 o Apache Bench para pruebas controladas de carga.
- Consola del gestor de base de datos para revisar consultas y registros.
- Herramientas de análisis estático propias del lenguaje.

Fase 1. Inspección y análisis estático

Propósito: identificar defectos potenciales en el código antes de ejecutar las pruebas.

Actividades:
1. Identificar los módulos principales de la aplicación.
2. Localizar las funciones responsables de conectarse con el servidor.
3. Identificar métodos de acceso a la base de datos.
4. Revisar validaciones, excepciones, condiciones y ciclos.
5. Ejecutar las herramientas de análisis estático.
6. Registrar advertencias, errores, dependencias desactualizadas y posibles problemas de seguridad.
Puntos de revisión obligatorios:
- Métodos sin manejo de excepciones.
- Credenciales o claves expuestas.
- Validaciones duplicadas o inexistentes.
- Código inaccesible o redundante.
- Consultas construidas con datos sin validar.
- Operaciones de red ejecutadas bloqueando el hilo principal.
- Recursos que no se liberan correctamente.
Evidencia: reporte del análisis estático y listado de defectos identificados.

Fase 2. Pruebas White Box de la aplicación móvil

Propósito: comprobar las rutas internas de ejecución y la lógica de negocio.

El estudiante seleccionará al menos tres métodos críticos de su aplicación:
- Un método de validación.
- Un método de procesamiento o cálculo.
- Un método de comunicación con un servicio o base de datos.
Para cada método deberá realizar:
1. Identificar sus instrucciones y condiciones.
2. Elaborar un grafo de flujo de control.
3. Identificar caminos independientes.
4. Diseñar casos de prueba para ejecutar los caminos identificados.
5. Comprobar los resultados mediante pruebas unitarias.
6. Obtener el porcentaje de cobertura.

Técnicas obligatorias:
- Cobertura de instrucciones (Statement Coverage).
- Cobertura de decisiones (Branch Coverage).
- Cobertura de condiciones (Condition Coverage).
- Pruebas de valores límite.
- Pruebas de excepciones.

Fase 3. White Box del sitio web y los servicios

Propósito: evaluar la implementación interna de los componentes web y de los endpoints.

Actividades:
1. Seleccionar al menos tres endpoints o funciones web relevantes.
2. Revisar los controladores, servicios, validadores y funciones que ejecutan las operaciones.
3. Probar rutas exitosas, errores de validación y excepciones.
4. Comprobar que los códigos HTTP correspondan al resultado real.
5. Verificar que la estructura JSON sea consistente.
6. Comprobar que no se expongan contraseñas, tokens o información sensible en las respuestas.
Códigos de respuesta que se deben evaluar cuando correspondan:
Código    Significado    Situación de prueba
200    OK    Consulta exitosa
201    Created    Registro creado
204    No Content    Eliminación sin cuerpo de respuesta
400    Bad Request    Datos mal estructurados
401    Unauthorized    Usuario no autenticado
403    Forbidden    Usuario sin permisos
404    Not Found    Recurso inexistente
409    Conflict    Conflicto de información
422    Unprocessable Content    Validación semántica fallida
500    Internal Server Error    Error inesperado del servidor

El estudiante deberá comprobar que el servidor no responda siempre con 200 ante operaciones fallidas y que no confunda errores de autenticación con errores de autorización.

Fase 4. Pruebas White Box de la base de datos

Propósito: analizar las operaciones internas de persistencia y su comportamiento.

Seleccionar al menos tres operaciones de base de datos de la aplicación y ejecutar:
1. Inserción de un registro válido.
2. Inserción con datos incompletos o inválidos.
3. Consulta por identificador existente.
4. Consulta por identificador inexistente.
5. Actualización de un registro.
6. Eliminación de un registro.
7. Consulta después de una operación para verificar persistencia.
8. Dos operaciones concurrentes sobre el mismo registro, cuando la arquitectura lo permita.
Revisar:
- Restricciones NOT NULL, UNIQUE y claves foráneas.
- Índices utilizados.
- Transacciones y operaciones parcialmente completadas.
- Consistencia entre los datos del servidor y los de la aplicación.
- Consultas ineficientes o que recuperan más información de la necesaria.
- Riesgo de inyección SQL, cuando se utilice SQL.
- Reglas de seguridad y permisos, cuando se utilice una base de datos en la nube.
Medición de consultas: registrar el tiempo de ejecución de al menos tres consultas. Cuando el gestor lo permita, utilizar el plan de ejecución (EXPLAIN o EXPLAIN ANALYZE).

Fase 5. Pruebas de conectividad y rendimiento

Propósito: evaluar la comunicación entre los tres componentes.

El estudiante deberá ejecutar mediciones desde el dispositivo o equipo cliente y registrar los resultados.

A. Ping y latencia de red
Registrar:
- Tiempo mínimo.
- Tiempo máximo.
- Tiempo promedio.
- Desviación estándar o variación de latencia.
- Porcentaje de paquetes perdidos.

B. Latencia HTTP
Medir el tiempo real que tarda el servicio en responder

C. Tasa de transferencia
Calcular la tasa de transferencia efectiva:
Tasa(Mbps)=(Bytes transferidos X 8) / Tiempo(s) X 1000000

Medir por separado la transferencia de subida y descarga, cuando el servicio lo permita.

D. Comparación de respuestas

Ejecutar diez solicitudes consecutivas al mismo endpoint, con los mismos datos y condiciones. Registrar el tiempo de respuesta de cada una, el promedio, el máximo y el mínimo.

E. Prueba de interrupción

Desactivar temporalmente la conectividad, ejecutar una operación y comprobar si la aplicación:
- Detecta el error.
- Evita mostrar una operación fallida como exitosa.
- Conserva o recupera los datos según su diseño.
- Reintenta de manera controlada, si corresponde.
- Evita duplicar registros al recuperar la conexión.
Importante: el ping mide latencia ICMP, no el tiempo de respuesta de la API. Algunos servidores bloquean ICMP; en ese caso se debe registrar la limitación y utilizar mediciones HTTP. No se deben interpretar ambas métricas como equivalentes.

Fase 6. Integración y reporte de defectos

Integrar los resultados y documentar al menos tres defectos, riesgos o áreas de mejora. Cada hallazgo debe incluir:
- Identificador.
- Componente afectado.
- Pasos para reproducirlo.
- Resultado esperado.
- Resultado observado.
- Severidad.
- Evidencia.
- Propuesta de corrección.

PRÁCTICA 12. Optimización, pruebas de estrés y resiliencia de aplicaciones móviles Flutter/Kotlin

Evaluar y mejorar el rendimiento, la escalabilidad y la capacidad de recuperación de una aplicación móvil propia mediante pruebas de estrés, análisis de cuellos de botella, profiling y optimización de sus componentes.

Objetivos específicos
- Identificar componentes que consumen recursos excesivos.
- Medir tiempos de ejecución y consumo de memoria y CPU.
- Evaluar la estabilidad de los servicios ante múltiples solicitudes concurrentes.
- Detectar problemas de saturación en la base de datos.
- Comprobar la recuperación ante errores de red y fallos de servicios.
- Implementar al menos una optimización real.
- Comparar cuantitativamente el comportamiento anterior y posterior a la optimización.

Fase 1. Recuperación de resultados de la auditoría anterior

Cada estudiante deberá revisar su reporte anterior y seleccionar:
- Un método de la aplicación con alto tiempo de ejecución o complejidad.
- Un endpoint con latencia elevada.
- Una consulta de base de datos que pueda optimizarse.
- Un problema de conectividad o recuperación.
- Un riesgo de consumo excesivo de memoria o CPU.
Debe elaborar una hipótesis técnica para cada problema.

Fase 2. Profiling y diagnóstico de la aplicación móvil

El estudiante ejecutará su aplicación y utilizará las herramientas de profiling.
Pruebas obligatorias
1. Ejecutar una operación de consulta repetidamente.
2. Ejecutar una operación de escritura.
3. Navegar entre las pantallas principales.
4. Realizar una operación que implique procesamiento de datos.
5. Observar el consumo de CPU y memoria.
6. Identificar bloqueos o retrasos en la interfaz.

Fase 3. Pruebas de estrés del sitio web y API

El estudiante seleccionará un endpoint de lectura y otro de escritura.
Resultados que se deben obtener
- Solicitudes por segundo (RPS).
- Tiempo promedio de respuesta.
- Latencia P90 y P95.
- Tiempo máximo.
- Porcentaje de errores.
- Códigos HTTP devueltos.
- Comportamiento del servidor durante la prueba.
Pregunta técnica: ¿el aumento de usuarios provoca un incremento proporcional en el tiempo de respuesta o existe un punto de saturación?

Fase 4. Pruebas avanzadas de base de datos

El estudiante deberá identificar una consulta crítica de su aplicación y ejecutar las siguientes pruebas:
1. Consulta individual por identificador.
2. Consulta de un conjunto pequeño de registros.
3. Consulta de un conjunto grande de registros.
4. Consulta con filtros.
5. Actualización de registros concurrentes.
6. Escrituras simultáneas sobre un mismo registro, cuando el motor lo permita.

Análisis obligatorio
- Tiempo de respuesta de cada consulta.
- Número de registros recuperados.
- Uso de índices.
- Bloqueos o esperas.
- Consultas repetidas innecesariamente.
- Problemas de concurrencia.
- Integridad de los datos después de las operaciones.

Elegir una consulta y mejorarla mediante alguna de las siguientes técnicas:
- Agregar índices.
- Implementar paginación.
- Recuperar únicamente los campos necesarios.
- Reducir consultas repetidas.
- Optimizar filtros y ordenamientos.
- Utilizar transacciones cuando sea necesario.
- Mejorar la estrategia de caché.

Fase 5. Pruebas de resiliencia y recuperación
En esta fase se provocarán fallos controlados para determinar si la aplicación puede continuar funcionando o recuperarse sin comprometer la información.
Escenarios obligatorios
Código    Escenario    Resultado esperado
RES-01    Pérdida de Internet durante una consulta    Error controlado
RES-02    Pérdida de Internet durante una escritura    No confirmar falsamente el registro
RES-03    Servidor sin respuesta    Timeout controlado
RES-04    Respuesta HTTP 500    Mostrar error y conservar estabilidad
RES-05    Respuesta HTTP 401 o 403    Gestionar correctamente autenticación o permisos
RES-06    Recuperación de conexión    Restablecer comunicación
RES-07    Reintento de una escritura    Evitar duplicados inesperados
RES-08    Respuesta tardía    Evitar operaciones duplicadas o inconsistentes en la interfaz

Análisis requerido
El estudiante deberá explicar:
- ¿Cuánto tarda la aplicación en detectar una interrupción?
- ¿Qué ocurre con una operación que queda pendiente?
- ¿Se repite automáticamente la solicitud?
- ¿Puede generarse un registro duplicado?
- ¿Cómo se recupera el estado de la interfaz?
- ¿Qué sucede si el servidor procesa la operación, pero la respuesta nunca llega al dispositivo?
Reto: proponer o implementar un mecanismo de reintento controlado con espera progresiva (exponential backoff) y una estrategia de idempotencia para las escrituras que lo requieran.

Fase 6. Optimización y comparación

El estudiante seleccionará uno de los problemas encontrados y realizará una corrección real.

Ejemplos:
- Optimizar una consulta.
- Reducir solicitudes HTTP innecesarias.
- Implementar paginación.
- Evitar operaciones pesadas en el hilo principal.
- Reducir el consumo de memoria.
- Corregir una fuga de recursos.
- Implementar un mecanismo de recuperación.
- Reducir el tamaño de las respuestas del servidor.
Después de implementar la mejora, repetirá las mediciones en las mismas condiciones.
